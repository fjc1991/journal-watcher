# Journal Watcher — development log

> Written for the original author's workflow: it keeps the design decisions, the gotchas and the history of each round. Where it says "the project folder" for data, today that is your data folder (`JW_HOME`); the repository itself holds no data. The first sections predate the repository layout.

_Last updated: 2026-10-22 (second session). Read this first if you're a new model picking up this project._

## 1. Goal

Weekly, on user trigger:
1. Check 7 journals for new papers (title/abstract/keywords).
2. Screen for the user's interests: **Open Innovation/OSS, GenAI (all topics), platform economics (all topics), decision support systems, ML/DL/RL**.
3. Download good matches into `Papers/YYYY-MM/<Journal Name>/`.
4. Read each PDF, write a markdown summary next to it, report key points.

Journals: **MIS Quarterly, Information Systems Research, Journal of MIS, Journal of the AIS, Information Systems Journal, Decision Support Systems, Management Science.**
(Excluded by user: EJIS, JIT, JSIS, Information & Organization, Information & Management.)

User: Nova SBE (Portugal) IS researcher. AIS + INFORMS memberships; Nova library SSO covers Wiley, T&F, Elsevier.
Cadence: weekly, manual trigger.

## 2e. Round 2 (added 2026-10-24): paper cards, folder evidence, the Research Ideas Lab

**Paper card (G4)** — reader tab **Card**: question, type, topics, theories (and their role), constructs, hypotheses (+ verdict), method (design / data / sample / analysis), findings,
contribution, implications, limitations (stated by the authors, or "inferred"), future research. The model sees the paper's body passages, numbered, and returns JSON (schema in
`papercard.SCHEMA`); every statement carries passage numbers, the program drops numbers that were never given, and the card stores each cited passage's page + opening words so a
click jumps there with no model involved. Click any text to edit (saved with a rev, marked ✎); ⟳ writes it again (old card → `state/card_backups/`); Copy / → Notes. Stored as
`<paper>.card.json` next to the PDF (listed by `notes_store.sidecars`, found by Library search, flagged `card` on library rows → 📇 chip). Cost shown first (`ai.estimate`).
Very long papers keep their start and end. A cut-off JSON answer is an error and is **not cached** (`ai.stream(cache_if=…)`).

**Folder tabs (Library → a folder):** **Papers** · **Evidence** · **💡 Ideas Lab**.
- *Evidence* (`evidence.py`): needs cards (one button makes the missing ones, three at a time, cost shown). Shows topics / theories / methods / constructs with how many papers share each, and
  **limitations and future-research suggestions grouped by meaning** (local embeddings, greedy clusters; a point several papers share is a gap). Every sentence opens its paper at the passage.
- *Ideas Lab* (`ideas.py`): 1 brief (focus, constraints, how many, ambition) → 2 **current events** (provider web search from the folder's topics; each event shows whether its URL was among the
  sources the search returned; untick or add your own — the model may only cite events listed) → 3 **generate** (ideas JSON with evidence ids P/L/F/E → ids checked by the program → grounding
  *grounded / partly / speculative*; no valid event ⇒ no "why now" text) → an **editor pass** scores novelty / feasibility / significance / fit (1–5) → **OpenAlex** lookup of the closest existing
  work, ranked by local-embedding closeness to the idea (honest "couldn't check" when offline). The **board** keeps ideas in `Papers/_folders/<id>.ideas.json` (rev-guarded): ★, shortlist, hide,
  note, delete, filter/sort, **Develop this idea** (proposal outline, saved), export Markdown / Word, or save into your **export folder** (Settings → Reader → Export folder, e.g. Dropbox).
  Each run keeps a snapshot of what P/L/F/E ids meant, so old ideas stay readable after the folder changes.
- Four new AI features in `ai.json`: `card`, `events` (must be a provider that can web-search), `ideas`, `critique` (all default to Claude; Settings → AI lists them).

**New files:** `scripts/{papercard,evidence,ideas}.py`, `static/{card,ideas}.js`, `static/ideas.css`. New routes: GET `/api/doc/card`, `/api/folder/{evidence,ideas}`, `/api/export/{ideas,cards}`;

**Tests:** `test_reader.py` +18 checks (cards, edits, batch, evidence clustering, events + retry, closest-work search, board saves, generation rules, develop, export), `test_ui.py` +26 (card tab, edits,
library chip, Evidence batch, Ideas Lab end to end incl. reload and export; screenshots 7–10 with `JW_SHOTS`).
**Verified against the real Claude API** on three real papers (about $0.57 in total, library untouched): a card takes 14–20 s and costs $0.07–0.10 (the estimate shown first was within ~15%);
events: the provider searched the web 1–3 times and returned dated events with real URLs (all found among the search sources); 3 ideas + editor ≈ $0.06, "develop" ≈ $0.07; OpenAlex found real close work.

## 2f. Round 2, second half (added 2026-10-24): ask a folder / the library, comparison matrix

**Folder tabs are now:** Papers · **Ask** · **Matrix** · Evidence · 💡 Ideas Lab. The Library also has an **Ask** tab (whole library, narrowed by folder / journal / year / tag / status).

**Ask several papers (`scripts/multiask.py`, `static/askmany.js`)** — numbered passages from *different* papers, each labelled with its paper (author, year) and page; the system prompt makes the model name the papers,
say where they agree or differ, and cite `(3)` / `(2,7)`; citations to passages it was never given are flagged. Two ways to read (a select in the tab): **passages** = the closest body paragraphs over all papers
(local embeddings, at most a few per paper so no paper drowns the rest; a paper is indexed the first time it is used — the tab says how many are new and roughly how long) or **cards** = the lines of each paper's card

**A fifth, found by CI (it led to a fix in the reader).** "clicking a page link turns to that page" (the `//2` note link) failed once on the macOS runner and passed on the sandbox. The cause is in the reader, older than this work and identical on `main`: `jump(n, 0)` sets the page-number box to `n` at once, then scrolls so that page `n`'s top lies **70 px below** the pane's top, while the scroll handler decides the current page with `currentPos()`, whose line is only **8 px** below the top; the previous page's foot is still in view above that line, so a few milliseconds later the box shows `n − 1` and stays there (measured: after typing 3 the box reads 3, then 2, with page 3 at 70 px). Measured before the fix on a 4-page PDF: typing 3 left the box on 2; after typing 2, Next went to 2 (it was already there), then stayed on 2, and Previous went to 1 (they work from `currentPos()` too: now 2, 3, 4, 3); and every zoom-in-then-out moved the text up by about a hundred pixels (scroll position 1500, 1386, 1272, 1157 over three cycles, with the box reading 1 by the third); after it: 1500 every time, and the box reads 3. The old numbers were a line 8 px below the top for reading and 70 px for jumping, so every restore shifted the text by the difference (scaled by the zoom). One consequence: the page number now changes when the next page's top passes the line 70 px below the top of the window, not 8 px, i.e. a little earlier while scrolling down. `test_ui.py` +3 (the box stays on the typed page for a second; Next and Previous follow it; three zoom cycles return the text to within 3 px) and one changed: the citation check had expected the page *above* the note's page (the box read 1 after opening a note on page 2) and now compares the box with the page the citation chip names (that page was 2: the fixed reader shows 2 and has it at the line; the old check had passed because it read the box before the reader had scrolled at all, while it still showed its starting `1`, so it was a race that happened to agree with the bug; the new one is correct but is not a reliable detector of the old bug: it passed on the old reader in one of my runs). The first three new checks were shown to fail on the old reader.

**Two review findings on that fix (collapsed view), both real, both fixed in the same pull request.** Copilot noted that `currentPos()` still answered "the strip at the line" only when the line falls on a strip. (1) *The line in a gap.* In the collapsed view the paper is strips separated by "⋯ N lines hidden" bars, and the reading line often lies on a bar; `currentPos()` then returned the *start of the next strip* and `jump()` put that start on the line, so every zoom, expand or collapse slid the text up by the distance from the line to the strip (measured: 28 px for one zoom step, with the bar's middle on the line; the same inexactness exists in the full view for the 10 px between pages). This is older than the 8 → 70 change (the old line met bars as often); I had not meant "zooming does not move the text" to stop at pages. (2) *The line below every strip.* When every strip ends above the line (a collapsed paper shorter than the line, or a very short window) the loop found nothing and returned `{n: 1, y: 0}`: the page number box read 1 while page 3 was on screen, and expanding went to page 1 (measured in a 130 px high pane). With the old 8 px line this needed strips shorter than 8 px, so the move to 70 px made it reachable; in a normal window it still needs a one-strip collapsed paper at the smallest zoom with Context 0 (a strip is then 7 px high under a 36 px bar), so it is an edge, but the answer was plainly wrong. The fix: `currentPos()` also returns `dy`, how far the returned point lies below the line (0 on a strip; positive in front of a strip; negative past the last strip, where the point is that strip's end), and `jump(n, y, {off})` puts the point `off` px below the line; the four places that restore a position after a layout change (zoom, the "lines hidden" bar's click, collapsing, expanding) pass `dy` back. ## 2o. A signed update feed and a release dry run (added 2026-10-28, second piece of work)

**The decision.** Until now an installed copy believed whatever `appcast.json` and zip were published under the release address, checked only against a sha256 that sits in the same feed: whoever controls the feed host (here: the GitHub account, or a changed release workflow) could ship code to every copy (§2l said so). The author chose a signature with a key **kept on the author's own Mac and used by hand** (the alternative, a key in GitHub secrets that CI signs with, protects against a damaged download but not against the account or the workflow being taken over, since either can use the secret).

**The protocol (`scripts/updater.py`, `app/sign_release.py`).** Ed25519 (PyNaCl; libsodium is inside the wheel). What is signed is `SIG_PREFIX` (`journal-watcher-appcast-v1` + newline) followed by the **exact bytes of `appcast.json`**; the signature (base64, 64 bytes) is the release asset `appcast.json.sig`, found at `<feed address>.sig`. The feed carries the zip's sha256, so the signature covers the zip too. The app checks the signature **before** parsing the feed. The public key(s) are built into the app: `app/update_public_key.txt` (one base64 key per line, `#` comments) is copied by `build_app.sh` into the bundle's `defaults/update_public_key.txt`. Rules, each with a test (and each shown to fail when I broke it on purpose): with no key built in nothing is checked, as before (a project run, a build made before the key exists, copies older than this); with a key, a feed with no signature (HTTP 404), a bad one, one made by another key, or one made without the prefix is **ignored** with a plain message (shown in Settings → About & updates); a key file that has lines but no usable key means *nothing* verifies (a damaged file must not switch the check off); more than one key may be listed, so a key change is shipped as an app that trusts both; with a key built in, nothing in `update_state.json` is believed except the **checked feed's bytes and signature** (`feed_data`, `feed_signature`): `public()` and `_run_install()` read them again and check them again with the keys the app has *now* (`cached_feed`) and take version, address, checksum and notes from those bytes; the fields beside them, which anything sharing the data folder (an older copy, a project run) can rewrite, are ignored, and a key taken out of the app stops vouching for what it signed (a first draft kept a `verified` flag instead; a review of the pull request showed that a flag is bound to neither the fields nor the keys); the download is still checked against the (now trusted) sha256 and the unpacked app still has to pass `codesign --verify` with the same bundle id and version. `JW_UPDATE_KEYS` replaces the key file (tests only).

**Signing by hand.** `python app/sign_release.py keygen` makes the key (`~/.journal-watcher/release-signing-key`, mode 600, refuses to overwrite, says to back it up) and prints the public half; `sign --tag vX.Y.Z [--upload]` downloads the release's `appcast.json` and zip, refuses unless the feed's address is **exactly** this repository's release zip address for the tag (always: with `--dir` and no `--tag` the tag is taken from the feed's version), the version equals the tag, and the zip's size and sha256, **recomputed here**, equal the feed's, prints version, notes and checksum, makes you **type the version**, writes `appcast.json.sig` and (with `--upload` and the `gh` tool) attaches it. `--dir` does the same for files downloaded by hand, which is the way while the repository is private. `verify` checks a signature against a key. **What a signature cannot say:** that the zip contains what the source says. It says the key holder looked at this version, address and checksum and approved them; trusting your own tag and workflow run is still on you. **Other limits:** a feed that is *frozen* (an old, validly signed one served again) cannot be told from a quiet month, but the app never installs anything not newer than itself, so it cannot be pushed back; if the key is lost, installed copies cannot be updated by themselves until people install an app built with a new key (hence the backup); a copy older than the first build that has a key does not check anything, so the update *to* that build is still taken on trust (and so is any update offered to a copy that never gets there); every update after it is checked. The feed's own address can still be changed in Settings; the `.sig` is then looked for next to it.

**Build.** `build_app.sh` copies the public key when `app/update_public_key.txt` exists (and says so when it does not), and after signing the app runs `Journal Watcher --jw-module updater` headless: `updater.py`'s `selfcheck()` signs and verifies a known message with libsodium and refuses a changed one, so a bundle without libsodium fails the build instead of shipping an app that silently cannot check (it runs even with `JW_SKIP_SELFTEST`, which only skips the window). `JournalWatcher.spec` names `nacl` and its parts as hidden imports (`updater.py` imports it only when it checks a feed). **Not verified here (Linux):** the PyInstaller bundle itself, and that hook; the self-check is what will tell.

**Release dry run (`release.yml`).** The workflow also has `workflow_dispatch` (Actions → release → Run workflow, optional version, default the newest `## x.y.z` of `CHANGELOG.md`): it builds the app, zip and disk image, writes the feed, rehearses `sign_release.py` on those files with a throw-away key (so the feed, the zip name and the address are checked against each other on the real artifacts), keeps `dmg`, zip, `appcast.json` and the notes for three days as run artifacts, and does **not** publish (the publishing step runs only for a tag). The version, tag and a hostile version input were exercised on a copy of the step's shell script; the YAML is linted with PyYAML (the first draft had unquoted `: ` in step names, which GitHub would have reported only when the workflow ran). **Not run:** the workflow itself, which needs a macOS runner. **A cost to know about:** as I understand GitHub's billing (check Settings → Billing), on a private repository macOS minutes count ten times against the free allowance and on a public one Actions are free, so a dry run (a build of perhaps 10 to 15 minutes) is a real spend until the repository is public; every push to a pull request already runs two macOS jobs.

**Tests.** `test_reader.py` +4 (the rules above against a local feed that also serves `.sig`; the key list; the signing script end to end with a key in a temp folder, its refusals, and mode 600; the build's own self-check run as `python updater.py`), `test_ui.py` +1 (Settings says whether the signature is checked). Two older things came up while running the suite for this: the full-text check can run in a moment when the result list is being drawn again, so it now waits for everything it needs at once (it also prints what it saw), and **one step I do not understand**: "Folders → Add paper" (`#adddlg[open]` after clicking `rail-add`) has stopped the suite three times in about a dozen runs (twice at normal speed, once at `JW_TEST_THROTTLE=2`; never on the CI runner so far) and not in the runs around them; nothing in this work touches it. The state printed on the fourth occurrence (my local run) was: no `#adddlg` had ever been made, no dialog open, three tiles, the rail button visible, route `#/folders` — i.e. the click reached nothing (the toast text in that dump is stale: the toast keeps its text after it fades). The most likely cause, not proved: the Folders page redraws itself when its tab is shown (`mount` → `draw`), and a click whose mouse-down comes just before the redraw is lost, like the Review tab's re-mount. The step now clicks again up to four times, as a person would, and still prints the state if all fail.

**The first dry run (2026-10-29): it failed, at the check this section added, and the check was right.** `release` run #1 (from `main`, `000cbdc`): the build environment, the icon and picture, PyInstaller (about a minute), the bundle and its ad-hoc signature all went through; then `update signature check FAILED: ModuleNotFoundError: No module named '_cffi_backend'` from `build_app.sh`'s own run of `Journal Watcher --jw-module updater`, which stopped the job. Cause: PyNaCl's libsodium binding is a compiled module (`nacl/_sodium.abi3.so`) that imports `_cffi_backend` from C; PyInstaller reads Python imports only, so it did not bundle it, and the spec's `nacl` hidden imports did not help. Nothing in the Linux suites could have found this (they run the Python files, not the frozen app, and the Mac app cannot be built on Linux), which is what the self-check in the build was for. **Reproduced on Linux** with PyInstaller 6.22 on a minimal program that signs and verifies with PyNaCl 1.6.2 (a scratch script, not kept): with the spec's exact `nacl` hidden imports the frozen program fails with the same error; with `_cffi_backend` added it prints "signature check ok". The spec now lists `_cffi_backend`. **Not verified on macOS** (Python 3.14, the runner's wheels) until the next dry run. The steps after the build had never run either, so their commands were rehearsed on Linux with a dummy zip, the feed an empty `previous.json` (what the workflow writes while the repository has no release): `make_appcast.py`, `sign_release.py keygen` and `sign --dir app/dist --tag v1.2.0 --repo fjc1991/journal-watcher` all pass; the zip and disk image steps (`ditto`, `dmgbuild`) are the author's own earlier tooling and were not rehearsed. Two more things for later: the dry run's "keep the results" step now also runs when the build failed and attaches PyInstaller's `warn-JournalWatcher.txt` (its list of modules it could not find) when it exists, and the finished app is still never *started* in CI (`JW_SKIP_SELFTEST=1`: no window session), so a missing module in the app's own start-up would show first on a Mac; a headless start of the frozen app's server (`--jw-module server`) and a request to `/api/config` would catch most of that, and is a possible next step. **The first successful dry run** (#2, `9c55fea`: every step green, 1 min 45 s for the build, an artifact of 299 MB) showed what the author saw on opening it: the installer lay at `dry-run-1.2.0/app/dist/Journal Watcher.dmg`, because `upload-artifact` keeps the common parent of all its paths. The dry run now sorts the files into two folders first and uploads two artifacts: `dry-run-<version>` holds only `Journal Watcher.dmg` at its top (one folder level remains: GitHub always zips an artifact, and the browser unzips it into a folder of that name), and `dry-run-<version>-details` holds the update zip, the feed, the notes and PyInstaller's warnings file (the second is also uploaded when the build failed). A real release was never affected: it attaches the files to the release itself, so people download `Journal Watcher.dmg` directly from the Releases page.
